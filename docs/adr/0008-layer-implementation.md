# Layers are one physics scene with separated geometry and a per-Layer observer condition

> **STATUS: ACCEPTED (2026-11-16).** Chosen by Fernando while answering the Phase 2 PRD (#31).

ADR-0004 made every interior a discrete Layer: a space connected to the rest of the map only by doors, with no sight or fire across the boundary. This ADR records how Layers are built in Unity and FishNet.

**All Layers live in one Unity scene, sharing one physics scene. Each Layer's geometry is placed physically apart from every other Layer's.** Interiors and the Undercroft sit far from the Surface footprint. A projectile or a collision therefore cannot cross a Layer, because the geometry never overlaps. The Phase 1 projectile sweep and CharacterController movement work unchanged.

**Replication is scoped per Layer by a custom FishNet observer condition, `LayerCondition`:**

- Every Layer-bound networked prefab carries:
  - a `LayerMember`, which holds a server-written Layer id that is replicated to clients for the HUD;
  - a `NetworkObserver` holding the condition.
- **Visibility rule:** a connection observes an object only when the object's Layer equals the connection's Layer.
- **`LayerService`** is a server-side component that sits beside each NetworkManager. It records each connection's Layer, and it is the single entry point for moving a Raider between Layers. Every move rebuilds observers.
- **Inheriting Layers:** objects spawned by a Layer-bound object inherit its Layer. Projectiles take the shooter's Layer; a loot bag takes the dead Raider's.
- **Effect:** players in other Layers do not replicate at all. This is the anti-wallhack freebie the vertical-slice plan counts on.

Gameplay code (doors, Waygates, Exfil, Hatches, and later AI) knows only Layer ids and calls `LayerService`. It never relies on how Layers are realised.

## Considered Options

- **One additive scene per Layer, using FishNet's `SceneManager` and `SceneCondition`.** It gives stronger isolation (per-scene physics, per-interior authoring, client memory that scales with huge maps). **Rejected** because it costs a lot of complexity now:
  - orchestrating scene loads, plus races between spawning an object and loading its scene;
  - a loading hitch at every door, at the tensest moment;
  - per-scene raycasts for projectiles;
  - a NavMesh per scene, which complicates Phase 3 AI entering Large interiors;
  - moving an object between scenes, on top of client-side prediction (ADR-0007).

  Its benefits target hand-authored or huge maps. Our maps are generated by code, and huge maps are deferred past the slice. Fernando judged that migrating to it later is not worth planning for.
- **FishNet's built-in `MatchCondition`, with Layer = match.** **Rejected** for a thin custom condition. `MatchCondition` keeps a global match registry, which is awkward with the test harness running several NetworkManagers in one process. A custom condition is about 30 lines and reads our own state.

## Consequences

- Static Layer geometry is loaded on every client all the time. That is negligible for a graybox map with about 8 interiors, and frustum culling keeps distant Layers from rendering.
- Non-networked scene objects (doors, `LayerInfo`) are identical on every peer because the scene is identical.
- A Layer transition is a teleport plus a `LayerService` move. Under client-side prediction, the teleport runs inside the replicate so the owner predicts it (#35).
